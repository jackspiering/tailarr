## P0 findings

### 1. P0 - Failed Apply rollback detaches running containers from their data

**Location:** `internal/deploy/deploy.go:220-239` (backup and restore defer), `internal/deploy/backup.go:248-290`
(`restoreDeploymentFromBackup`).

Apply copies the whole deployment directory to `.tailarr_backups`, including container data. On any later failure the
restore defer renames the live `dest` to `.partial-<service>`, renames the backup into `dest`, and then runs
`os.RemoveAll(partial)`:

```go
if err := os.Rename(dest, partial); err != nil {   // backup.go:276
...
if err := os.Rename(backupPath, dest); err != nil { // backup.go:280
...
    _ = os.RemoveAll(partial)                       // backup.go:288
```

A common Apply failure is a failed `pull`. At that point the old containers are still running. Their bind mounts
point at the inode of the original directory, not at the path. After the restore:

- the running containers write into a directory that Tailarr just deleted,
- data written between the backup and the failure is lost,
- the Tailscale sidecar loses `ts/state` the same way.

**Evidence (runtime):** A throwaway integration test deployed a busybox service. It ran as `user: "1234:1234"` and wrote a
counter to `./data/heartbeat` every second. The test then broke the template image and ran `Apply`:

```text
apply err: apply failed; previous deployment restored: docker compose failed: ... pull: exit status 1
host heartbeat after restore: "2" then "2"   (the host file no longer changes)
container view of /data/heartbeat: "cat: can't open '/data/heartbeat': No such file or directory"
container ls /data: total 0
```

The operator sees `previous deployment restored`, but the running service now writes into a deleted directory. The
functional check marked this path as Pass because it compared files on disk, not the running container.

**Suggested fix:**

1. Scope the Apply backup to the files Apply writes: every template-relative path, `.env`, and `.tailarr.compose.yaml`.
   Apply never touches container data, so it never needs to restore container data. Restore those files in place with
   `atomic.WriteFile` (or remove files that Apply created). Do not rename the deployment directory.
2. If the failure happened after `up` started, run `up -d` again with the restored files. Use `composeCleanup` so it
   still runs after an interrupt. Then the containers match the restored config.
3. Add an integration test like the one above. It must assert that the container still sees its data after a failed Apply.

### 2. P0 - Backups drop ownership and group permissions

**Location:** `internal/deploy/backup.go:145-186` (`copyTree`, `copyFile`).

`copyTree` creates directories with `os.MkdirAll(target, info.Mode().Perm())` and files with `os.OpenFile(..., mode)`.
Both go through the umask, and neither calls `Lchown`. Every copied file is owned by the user who runs Tailarr. Most
ScaleTail apps run as `PUID`/`PGID` 1000 or as a service uid. Tailarr runs as root for Apply and Remove (README:120-121).
So a restored backup is root-owned, and group-write bits are lost.

**Evidence (runtime):** Same test as finding 1, after `docker restart` so that the container binds the restored directory:

```text
before apply ownership: coder:coder 777 .../rvw/data, UNKNOWN:UNKNOWN 644 .../rvw/data/heartbeat   (uid 1234)
after restore ownership: coder:coder 775 .../rvw/data, coder:coder 644 .../rvw/data/heartbeat
container logs after restart: sh: line 0: can't create /data/heartbeat: Permission denied
```

**Suggested fix:** Finding 1's scoped backup removes most of the exposure. Any remaining full-tree copy (Remove) should
preserve metadata: `os.Lchown(target, stat.Uid, stat.Gid)` when running as root, `os.Chmod` after creation so the umask
does not apply, and mtimes with `os.Chtimes`. Preserving hard links and xattrs is optional. Add a test that copies a
0664/0775 tree and asserts the modes.

## P1 findings

### 3. P1 - Backup copies all container data: FIFOs hang forever, sockets fail, size is unbounded

**Location:** `internal/deploy/backup.go:145-186`, callers `deploy.go:220` (Apply) and `deploy.go:598` (Remove).

`copyTree` sends every non-directory entry to `copyFile`, which calls `os.Open(src)`. It never checks
`info.Mode().IsRegular()`.

**Evidence (runtime):** Throwaway unit test:

```text
socket: backup err=copy deployment to backup: open .../svc/data/app.sock: no such device or address
fifo: backup still blocked after 5s
```

- A named pipe blocks `open(2)` until a writer appears, which can be never. The copy does not check any context. The
  SIGINT handler (`app.go:205-212`) waits for in-flight work before it quits. So Ctrl+C cannot stop Tailarr, and the
  service lock and catalog lock stay held until `kill -9`.
- A Unix socket (common in app data, for example database or supervisor sockets) makes every Apply and Remove fail.
- Media libraries or databases under the service directory are copied in full on every Apply and Remove. There is no size
  check and no progress output. A live database copied while it runs is not a consistent backup.

**Suggested fix:** In `copyTree`, skip sockets, FIFOs, and devices with a logged warning. Only regular files and
directories are copied. With finding 1, Apply backs up only managed files, which removes the size problem there. For
Remove, back up managed files by default. Offer a data backup after showing its size (`du`-style walk), or document that
Remove keeps no data backup. Check `interrupt.Context()` between files so Ctrl+C can stop a long copy.

## P2 findings

### 4. P2 - Git prompts cannot be answered; Refresh hangs until the 5 minute timeout

**Location:** `internal/scaletail/repo.go:35-49` (`runGit`), `internal/scaletail/gitproc_unix.go:16` (`Setpgid: true`).

`runGit` starts git in its own process group and captures its output with `CombinedOutput`. It does not set
`GIT_TERMINAL_PROMPT=0` or SSH batch mode. When git needs input, it writes a prompt to `/dev/tty` and then reads from a
background process group. The operator cannot answer. This happens with an HTTPS repository that needs credentials, or a
first `git@`/`ssh://` connection that asks to confirm the host key. Both URL forms are accepted by `ValidateRepoURL`.

**Evidence (runtime):** `Refresh("https://gitlab.com/<missing>/repo.git", ...)` under a pseudo-terminal, with
`gitOpTimeout` shortened to 15 s:

```text
Username for 'https://gitlab.com':     elapsed 15s err=ScaleTail git clone failed: git operation timed out after 15s
(check network and retry; ...)
```

With the production timeout the TUI waits 5 minutes, then blames the network.

**Suggested fix:** Set `cmd.Env = append(os.Environ(), "GIT_TERMINAL_PROMPT=0")`. When `GIT_SSH_COMMAND` is not already
set, also add `GIT_SSH_COMMAND=ssh -o BatchMode=yes`. Git and ssh then fail at once with an authentication error. Add a
hint to the error: configure a credential helper or SSH agent, and accept the host key once with `ssh -T <host>`.

### 5. P2 - Refresh keeps pulling the old origin after the repository URL changes

**Location:** `internal/scaletail/repo.go:73-83`.

When `<repo>/.git` exists, `Refresh` runs `pull --ff-only` and never compares `origin` with `repoURL`. An operator who
switches to a fork or mirror in Configuration gets "Catalog refreshed." while the catalog still comes from the old
remote. Doctor also prints the new URL, which adds to the confusion.

**Suggested fix:** Before pulling, run `git -C <repo> remote get-url origin` and compare it with `repoURL`. On a mismatch,
refuse with a clear message ("catalog clone tracks X, config says Y; remove <repo> or run Refresh with confirm to
re-clone"). Alternatively, after a confirm, run `git remote set-url origin <repoURL>` and fetch.

### 6. P2 - A batch keeps running after Ctrl+C

**Location:** `internal/ui/app.go:1045-1065` (`runBatch` loop).

After SIGINT, `drainThenQuit` cancels the shared context and waits for the batch to return. `runBatch` does not check that
context, so it starts every remaining service. Each service takes its lock and runs `copyTemplate`, or the full-tree
`Backup` for Apply and Remove (finding 3). Only then does it fail on the canceled compose or prompt. For a 10-service Apply
of data-heavy apps, Ctrl+C can take minutes to exit.

**Suggested fix:** At the top of each iteration, stop when `interrupt.Context().Err() != nil`. Also stop when the last
error `errors.Is(err, deploy.ErrInterrupted)` or `context.Canceled`. Append `"  skipped: interrupted"` for the services
that did not run. A per-service `prompt.ErrCanceled` (operator answered No) should still continue.

### 7. P2 - Locks are held across interactive prompts

**Location:** `internal/deploy/deploy.go:166-218` (Apply takes the service lock and catalog lock before `Confirm`),
`deploy.go:64-73` plus `mergeAndWriteEnv` (Deploy prompts for env values and auth keys under both locks).

The catalog lock is shared by every Deploy, Apply, and catalog Refresh (`lockRepo`, `runCatalogRefresh`). While one
operator reads an Apply confirm or types env values, a second Tailarr instance or terminal waits 30 s. It then fails with
`another Tailarr process holds the lock`, even for an unrelated service.

**Suggested fix:** Ask for confirmation and collect answers first. Then take the locks and check again that nothing
changed (managed marker present, template still valid). For Deploy, parse the template `.env` under the catalog lock,
release it, prompt, then lock again and compare a template hash before writing. At minimum, release the catalog lock after
the template is copied, because the prompts do not read the catalog.

## P3 findings

### 8. P3 - Failures are not logged

`Manager.log` is called only on success paths (`deploy.go:132, 263, 538, 559, 624`). `runBatch` prints errors to the
result panel (`app.go:1060-1061`) and never logs them. After the TUI closes, a failed Deploy, Stop, Restart, or Remove
leaves no trace. This is still open from functional check F7. **Fix:** in `runBatch`, call
`log.Event(fmt.Sprintf("%s %s failed: %v", action, svc, err))`. `Event` already redacts.

### 9. P3 - Config edit writes environment overrides into the config file

`config.Load` applies `TAILARR_*` overrides to the same struct that the TUI edits (`config.go:145-190`).
`editConfigInteractive` uses those values as defaults and saves all fields (`app.go:802-833`). A one-off
`TAILARR_DEPLOY_PATH=/tmp/x tailarr` session followed by a config edit makes `/tmp/x` permanent. **Fix:** keep the
file-only config beside the effective config. Edit and save the file-only copy, and show which fields an environment
variable overrides.

### 10. P3 - Shared batch key edge cases

In `runBatch` (`app.go:1026-1044`), `sharedKey = s.Keys[name]` returns empty for a mistyped name and silently falls back
to the paste prompt. The pasted value is not checked with `names.ValidTSAuthkey`. Every service then fails
with the same error, after each one copies its template. The `Line` error is also ignored (`name, _ :=`). **Fix:** reject
an unknown name, validate the pasted key once, and return on prompt errors.

### 11. P3 - No summary confirm before a batch

`a` selects every row (`app.go:396-401`) and `Run on selection` starts at once (`app.go:942-972`). Deploy, Stop, and
Restart have no confirm, so two keys can deploy the whole 122-service catalog or stop every stack. **Fix:** before
`startSequence`, show "Deploy 12 services: a, b, c ...? [y/N]". Also add `n` to clear the selection.

### 12. P3 - Restart leaves the service down when `up` fails

`Restart` runs `stop` then `up -d` (`deploy.go:547-562`). If `up` fails (image pruned, port taken), the service stays
stopped. The error does not say that Restart stopped it. **Fix:** say so in the error ("service is stopped; run Apply or
Restart again"). Or try `up -d` without `--remove-orphans` once more before reporting.

### 13. P3 - Backup deletion errors are ignored

`RemoveWith` runs `_ = safeRemoveTree(b, root)` for each backup and then logs `removed N backups` (`deploy.go:616-619`).
Backups can hold `.env` secrets, and a root-owned tree fails for a non-root operator. **Fix:** count failures, show
"could not delete X; it may contain secrets", and log the real count.

### 14. P3 - Self-upgrade has an integrity check but no authenticity check

`Upgrade` downloads the binary and `SHA256SUMS` from the same release (`upgrade.go:197-213`). This catches a corrupt
download, but not a replaced release. The release workflow already creates build provenance attestations
(`release.yml`, `attest-build-provenance`). **Enhancement:** verify the attestation, or sign `SHA256SUMS` (minisign or
cosign keyless) and embed the public key or identity in the binary. The installer could do the same when `gh` or
`cosign` is present.

### 15. P3 - Open functional check items F5 and F8

- `runCatalogRefresh` still returns `Catalog refreshed.` followed by git's `Already up to date.` (`app.go:1012-1018`).
  Match `Already up to date` and return `Catalog is up to date.`.
- "Search available services" still lists every name with no query (`app.go:602-617`). The output now scrolls, but a
  filter prompt, or type-to-filter in the multi-select, would make both screens usable with 122 services.

### 16. P3 - Doctor misses two common blockers

`doctor.Run` (`doctor.go:327-371`) does not check `/dev/net/tun`, which ScaleTail sidecars need. It also does not warn
that Apply and Remove need root when the deployment tree holds root-owned container data (README:120-121). **Fix:** add a
`tun` check (`os.Stat("/dev/net/tun")`, char device). Add an `info` line when `os.Geteuid() != 0` and the deploy root
has deployments.

### 17. P3 - Prompt order for extra keys is random

`PlaceholderKeys` walks `merged` as a map for keys outside the template order (`env.go:230-237`). A deployment that has
several local-only empty keys prompts in a different order on each run. **Fix:** collect those keys and `sort.Strings`
them, as `WriteEnvFile` already does.

### 18. P3 - Stale installer comment

`scripts/install.sh:9` says `else v0.5.0`, while `DEFAULT_VERSION="v0.6.0"` on line 21. **Fix:** refer to
`DEFAULT_VERSION` instead of a literal version, so release prep does not need to touch the comment.

## Verified-clean areas

- **Secret handling:** No secret reaches argv, logs, or the TUI unredacted. `filterComposeEnv` drops secret-like and
  `COMPOSE_*` variables. `.env` and the key store are written mode 600 atomically. The `redact` package covers the
  suffix, JSON, colon, and URL forms from the previous review.
- **Symlink posture:** `JoinUnder`, `RefuseSymlinkAncestry`, `OpenFileNoFollow`, and the managed-file checks are applied
  on every lifecycle entry point. The non-root Stop and Restart fix (#51) walks only managed inputs.
- **Locks:** The O_EXCL plus flock design with in-place reclaim, token-bound `Release`, and the create-then-flock back-off
  are sound for single-host use.
- **Compose execution:** Interrupt handling, `WaitDelay`, cleanup `down` on a fresh context (#52), and `stop` + `up` for
  sidecar restarts (#50) behave as documented.
- **Release pipeline:** Tag format, reachability from `main`, metadata agreement, pinned actions, least-privilege publish
  job, and draft-only publication all match AGENTS.md.
